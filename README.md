# ACTOM QGrid — Inspections

Phase 1 of the ACTOM QGrid system. One codebase, one schema, **one database and one site per division**.

---

## The deployment model in one paragraph

Every division gets its own Supabase project and its own Netlify site. They all run the
**same commit** of the same repository. What differs between divisions is data —
manufacturing stages, product families, defect codes, inspection templates, the
requirements matrix, whether hold points are switched on. None of that lives in code.

```
                    GitHub: actom/qgrid-inspections
                                  │
                  ┌───────────────┼───────────────┐
                  │               │               │
            Netlify MVS     Netlify DTX     Netlify R&M     ← same commit
                  │               │               │            different env vars
            Supabase MVS    Supabase DTX    Supabase R&M   ← same schema
                                                              different data
```

**The rule that keeps this manageable: differences are data, never code.** The moment a
division needs its own branch, you stop having one product and start having 27. If a
division needs behaviour the others do not, add a setting, not a fork.

### Why separate databases

A bad deploy or a bad query in one division cannot touch another's records. Divisions
carry their own certificates and their own auditors, and a division can be restored to a
point in time without co-ordinating with 26 others.

### What it costs

27 Supabase Pro projects instead of one, and every schema change has to reach 27
databases in the right order. The first is a line item; the second is a real operational
risk, which is why `verify-drift.mjs` runs nightly. If cost becomes the deciding factor,
the alternative is a single database with `division_id` on every table and RLS doing the
isolation — cheaper, but one mistake in one policy exposes every division to every other.
The separation is worth paying for.

## Repository layout

```
supabase/migrations/     numbered SQL, applied in order to every division
db/seed/                 reference data (group) and per-division seed
divisions/registry.json  which divisions exist, their refs and status — no secrets
scripts/                 config generation, migration runner, drift check, provisioning
.github/workflows/       verify on PR, migrate on release, drift nightly
lib/supabase.js          client — byte-identical on every site
config.js                GENERATED at deploy time, never committed
```

---

## Branches

| Branch | Deploys to | Purpose |
|---|---|---|
| `main` | staging site (one, shared) | day-to-day work |
| `production` | every division site | releases |
| `release/<CODE>` | that division only | **exception** — a division that must lag |

Merging `main` → `production` releases to all live divisions at once. That is deliberate:
staggered code versions across divisions is the failure mode this whole structure exists
to avoid. A `release/<CODE>` branch is available when a division genuinely cannot take a
change during a critical window, but every one that exists is a debt to be paid down.

---

## Secrets

| Where | What | Notes |
|---|---|---|
| Netlify site env | `SUPABASE_URL`, `SUPABASE_ANON_KEY`, `DIVISION_CODE`, `DIVISION_NAME` | anon key is public by design — RLS is the control |
| GitHub Actions secrets | `DB_URL_<CODE>` per division | service-role connection, migrations only |
| Nowhere | service-role key in the browser | if this appears in client code, stop |

`config.js` is generated by `scripts/gen-config.mjs` at build time and is gitignored, so
no division's details are ever committed and the same commit deploys everywhere.

## Runbooks

### Release a schema change

```bash
supabase migration new add_something        # creates a timestamped file
# edit supabase/migrations/<ts>_add_something.sql
supabase db reset                           # prove it locally from scratch
git checkout -b feat/add-something && git push
```

Open a PR into `main`. The verify workflow applies every migration to a throwaway
Postgres from scratch and refuses to merge if any table lacks RLS. Merge `main` →
`production` and the migrate workflow pushes to every live division, then checks drift.

**Migrations run before Netlify finishes building.** An app expecting a column that does
not exist yet is a worse outage than a schema with a column nothing uses yet. Write
migrations additively: add the column, deploy the app, backfill, remove the old column in
a later release. Never drop and add in one step.

### Add a division

```bash
export SUPABASE_ACCESS_TOKEN=... SUPABASE_ORG_ID=... NETLIFY_AUTH_TOKEN=...
export DB_PASSWORD_NEW=... GITHUB_REPO=actom/qgrid-inspections
node scripts/new-division.mjs --code DTX --name "ACTOM Distribution Transformers"
```

Creates the Supabase project, applies every migration, seeds reference data, creates the
Netlify site, sets its environment variables and updates the registry. Then, by hand:

1. Add the site's callback URL to the ACTOM Entra app registration and enable the Azure
   provider on the new Supabase project.
2. Add `DB_URL_DTX` to the GitHub Actions secrets — **until this exists, the division
   silently stops receiving migrations.**
3. Point the custom domain at the site.
4. Load the division's product families, equipment and requirements matrix.
5. Commit the updated registry.

### Migrate one division by hand

```bash
node scripts/migrate.mjs --division MVS
node scripts/migrate.mjs --all --status pilot,live --dry-run
node scripts/verify-drift.mjs
```

## Authentication

One Entra app registration for the ACTOM tenant, with a redirect URI per division site.
Each Supabase project has the Azure provider configured against that same registration.
A user signs into their own division's site; a person who works across divisions has a
profile in each database. There is no cross-division login, by design.

New users arrive `active = false`. An authenticated session is not access — an
administrator activates them and assigns a role.

---

## Group reporting

Twenty-seven databases cannot be queried together. When group-level quality reporting is
needed, do **not** open cross-database connections. Have each division push a nightly KPI
snapshot — counts and rates, no source records — to a separate group Supabase project via
a scheduled function. Reporting reads only the group project, and no division can reach
another's data. Worth designing before the analytics module in a later phase, not after.

## Open items

- **Works orders come from SYSPRO.** Phase 1 assumes manual entry. A live read is a
  Phase 2 conversation and should not collide with the 5 October JTU go-live.
- **Region.** `eu-west-1` is the default in the provisioning script. If data residency
  requires it, Supabase has no South African region — that needs a decision on record
  before the first division goes live, not after.
- **Backups.** Supabase Pro gives daily backups with 7-day PITR per project. For records
  that have to survive an ISO audit cycle, add a weekly logical dump to ACTOM storage.
